## Methodology

- **Inputs** are generated deterministically (seeded PRNG) into a temp directory and deleted afterwards:
  - `records`: a top-level JSON array of event-log style records (about 0.5 KB each: nested objects, arrays, floats, booleans, nulls, non-ASCII text). The search term appears in the `message` of about 1.5% of the records.
  - `keyed`: the same records stored as one object (`{"r0":{...},"r1":{...}}`) instead of an array, used for unflatten only. It is included because some gron implementations rebuild large arrays much more expensively than large objects, so the array-shaped `records` input alone could mislead.
  - `deep`: `{"a":{"a":{...1}}}` nested N levels. Flattening it emits N lines whose paths grow with the depth, so the output is quadratic in N.
  - `bigint`: records with integers beyond 2^53 (12345678901234567890 and up) and decimals with trailing zeros (1.10).
- **Timing**: wall time of `bash -c '<command>'` under `/usr/bin/time -l`, which includes process start-up (for gronify, Node start-up). Output goes to `/dev/null`. The search workloads print one number and the capped workloads ten lines; those few bytes are captured to validate the run.
- **Runs**: the reported time is the median of 3 runs (set with `--runs`) for every workload. All run times and per-attempt RSS/status are in the JSON (`trials`; successful times also in `samples`). A run that fails ends that tool's measurement for the workload.
- **Raw evidence**: `trials` retains every attempt, including failures and OS-kill retries; `samples` retains successful times. Peak RSS is the median of per-attempt process peaks, independently aggregated from time. The source commit, runtime source hashes, built JS hashes, executable hashes and harness hash are in `provenance`. This source build is not necessarily the published npm package.
- **Fairness of order and cache**: the input is read once to warm the page cache immediately before every single run, and the tool order rotates from round to round, so no tool always runs first or benefits from another tool's warm-up.
- **Ties**: results within 5% of the fastest time in a column are a tie. They are not bold and carry `isTie` in the JSON; only a result that is more than 5% ahead of every other is bold (`isFastest`).
- **Peak RSS** is the maximum resident set size reported by /usr/bin/time, which for a pipeline is the largest single process in it (not the sum). The displayed RSS is the median of the successful per-run peaks, independently aggregated from elapsed time.
- **Limits**: each run is killed after 60 s (status `timeout`) or when its process tree exceeds 8 GiB (status `failed`, to protect the machine from tools that load the whole document). A SIGKILL that the script did not send is reported as a possible OS out-of-memory kill (the cause is unverified); it is retried once, and skips are not cascaded from a single OS kill. Otherwise a tool that fails or times out at one size is not run at larger sizes. A tool whose previous size, scaled linearly, would take more than 2x the timeout is also not run (`over-budget`, with the projection in the note), and so is everything once the 45 min total budget is used up; these are time-budget shortcuts, not measurements.
- **Fair equivalents**: each tool is run the way its documentation suggests for the job, in its default mode unless stated. Notes on the choices:
  - Correctness checks cover small representative documents. Full timed flatten/unflatten streams are discarded; stable piped byte counts are not proof of full-output equality. Search counts are checked on each timed workload. Legacy MB/GB labels use MiB-sized generated targets: 1000 MB means 1000 MiB (about 0.977 GiB), not 1 GiB. Record boundaries can slightly overshoot the target; exact bytes are recorded in JSON. Raw notes from the preserved invocation also use MB/GB for binary units; current memory cells use MiB/GiB.
  - gron sorts its output by default and reads the whole document before printing; `gron --no-sort` is listed separately. gronify and fastgron keep document order, so `gron --no-sort` is the closest like-for-like (it does not guarantee document order).
  - gronify search is case-insensitive by default; `--case-sensitive` is used so that it matches `grep`. Search matches whole gron lines (path and value) for all gron-style tools. A search result whose count differs from the exact number of occurrences counted while generating the input is marked failed.
  - `fastgron -F` is fastgron's native fixed-string filter; it is listed next to `fastgron | grep` for search.
  - jq and jaq do not produce gron. For jq the closest honest equivalent is `jq --stream -c .`, which emits one `[path, leaf]` event per leaf (plus closing events) with constant memory. jaq has no `--stream`, so it runs `paths(scalars|true) as $p | [$p, getpath($p)]` on the fully parsed document. That is the fastest idiom that still reports every leaf: plain `paths(scalars)` is faster still but silently drops null and false values, and a hand-written `path(..)` filter is about 1.8x slower. It omits empty containers. Their output is not byte-compatible with gron, and they cannot read gron statements, so they are not run for unflatten.
  - Capped workloads compare early exit: gronify `--limit`/`--max-count` stop reading the input; the others run through `head -n 10` or `grep -m 10`, which stops the pipeline only if the producer notices the closed pipe. Tools that must read and parse the whole document first (gron, jaq) cannot exit early. The matches are near the start of the file, which is the favorable case for early exit.
  - The unflatten input is `fastgron --semicolon` output (gron-format statements in document order) for every tool, since gron needs the trailing semicolons. gronify and `fastgron -u --no-indent --no-newline` write compact JSON. gron has no compact mode and writes indented JSON, so it writes more bytes to `/dev/null` than the others.
  - **Output sink**: the main flatten workloads write to `/dev/null`, which costs nothing. Some tools behave very differently when the output is consumed through a pipe (a deeply nested document can be several times slower into a pipe than into /dev/null), so `flatten, output piped to wc -c` repeats flatten with `| wc -c` for the deep documents and the records up to 100 MB. Read the two tables together; neither alone describes what a user piping into grep or a file will see.
- **Correctness checks** are run on small documents before timing and are listed at the end of this file. They are not timed.

| round-trip check | gron | `gron $INPUT \| gron -u` |
| round-trip check | fastgron | `fastgron $INPUT \| fastgron -u --no-indent --no-newline` |
| round-trip check | jq | `jq --stream -c . $INPUT \| jq -c -n 'fromstream(inputs)'` |

## Reproduce
