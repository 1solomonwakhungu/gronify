## Methodology

- **Inputs** are generated deterministically (seeded PRNG) into a temp directory and deleted afterwards:
  - `records`: a top-level JSON array of event-log style records (about 0.5 KB each: nested objects, arrays, floats, booleans, nulls, non-ASCII text). The search term appears in the `message` of about 1.5% of the records.
  - `keyed`: the same records stored as one object (`{"r0":{...},"r1":{...}}`) instead of an array, used for unflatten only. It is included because some gron implementations rebuild large arrays much more expensively than large objects, so the array-shaped `records` input alone could mislead.
  - `deep`: `{"a":{"a":{...1}}}` nested N levels. Flattening it emits N lines whose paths grow with the depth, so the output is quadratic in N.
  - `bigint`: records with integers beyond 2^53 (12345678901234567890 and up) and decimals with trailing zeros (1.10).
- **Timing**: wall time of `bash -c '<command>'` under `/usr/bin/time -l`, which includes process start-up (for gronify, Node start-up). Output goes to `/dev/null`. The search workloads print one number and the capped workloads ten lines; those few bytes are captured to validate the run. The reported time is the best of N runs (5 runs up to 16 MB, 3 up to 200 MB, 1 above). The page cache is warmed with one read of the input first, so the numbers measure CPU and memory behavior, not the disk.
- **Peak RSS** is the maximum resident set size reported by `/usr/bin/time -l`, which for a pipeline is the largest single process in it (not the sum), taken from the same run as the reported time.
- **Limits**: each run is killed after 120 s (status `timeout`) or when its process tree exceeds 28 GB (status `failed`, to protect the machine from tools that load the whole document). A tool that fails or times out at one size is not run at larger sizes. A tool whose previous size, scaled linearly, would take more than 2x the timeout is also not run (status `skipped`, with the projection in the note); this is a time-budget shortcut, not a measurement.
- **Fair equivalents**: each tool is run the way its documentation suggests for the job, in its default mode unless stated. Notes on the choices:
  - gron sorts its output by default and reads the whole document before printing; `gron --no-sort` is listed separately. gronify and fastgron keep document order, so `gron --no-sort` is the closest like-for-like (it does not guarantee document order).
  - gronify search is case-insensitive by default; `--case-sensitive` is used so that it matches `grep`. Search matches whole gron lines (path and value) for all gron-style tools.
  - `fastgron -F` is fastgron's native fixed-string filter; it is listed next to `fastgron | grep` for search.
  - jq and jaq do not produce gron. The closest honest equivalent for jq is `jq --stream -c .`, which emits one `[path, leaf]` event per leaf (plus closing events) with constant memory. jaq has no `--stream`, so it runs a path/leaf extraction filter on the fully parsed document, which is closer to the "flatten" jq idiom `paths(scalars)` but keeps nulls and empty containers. Their output is not byte-compatible with gron, and they cannot read gron statements, so they are skipped for unflatten.
  - Capped workloads compare early exit: gronify `--limit`/`--max-count` stop reading the input; the others run through `head -n 10` or `grep -m 10`, which stops the pipeline only if the producer notices the closed pipe. Tools that must read and parse the whole document first (gron, jaq) cannot exit early. The matches are near the start of the file, which is the favorable case for early exit.
  - The unflatten input is `fastgron --semicolon` output (gron-format statements in document order) for every tool, since gron needs the trailing semicolons. gronify's unflatten output is compact JSON, gron's and fastgron's is indented, so they write different numbers of bytes to `/dev/null`.
- **Correctness checks** are run on small documents before timing and are listed at the end of this file. They are not timed.

## Reproduce

```bash
brew install gron fastgron jq jaq   # any missing tool is recorded as skipped
cd src/packages/cli
npm ci && npm run build
npm run bench:compare               # about 20 minutes with the default sizes; needs a few GB of free temp space and RAM
npm run bench:compare -- --sizes 10 --deep 2000 --out-json /tmp/r.json --out-md /tmp/r.md   # quick run
```

Results depend on the machine, the tool versions and the generated data; compare tools within one run of this table rather than across machines.
